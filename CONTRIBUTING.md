# Contributing

kjk is written mostly by LLM agents, directed and reviewed by the
maintainer, who makes the decisions. This file is for anyone else working
in the repository, by hand or with an agent of their own.

## Getting started

1. Build and run it as [`README.md`](README.md) says ("Development").
2. Install the pre-commit hook, once per clone:

   ```bash
   cargo xtask hooks
   ```

3. Read, in this order: [`AGENT.md`](AGENT.md) (the rules that never bend,
   the gate, parallel work), [`docs/INDEX.md`](docs/INDEX.md) and the doc
   for the area you touch. [`ROADMAP.md`](ROADMAP.md) holds the why: the
   goals, principles and decisions. [`QUIRKS.md`](QUIRKS.md) lists the
   reference bugs we keep on purpose; check it before "fixing" one.

[`CONTEXT.md`](CONTEXT.md) is the maintainer's own workflow (the journal
under `context/`, slices). You do not need it to change the runtime.
`context/` is the maintainer's local, untracked research folder: links
into it from the docs point at files you will not have.

## The rules that never bend

The full list is in `AGENT.md`. The ones that bite first:

- **No game data, ever**: not in commits, issues, pull requests, tests or
  screenshots of extracted files. Test fixtures are data we make ourselves.
  The pre-commit hook (`cargo xtask publish-check`) refuses the shapes it
  knows; it cannot catch everything.
- **Game installs are read-only.** Nothing writes into them.
- **Machine paths live in `.env`**, never in code or docs.
- **Reference code is read, not copied.** reone, xoreos and OpenJK are GPL;
  kjk is MIT. Describe the behaviour you match in your own words and
  show that ours matches it. No original addresses or decompiler names
  (`FUN_…`).
- **The games' own rules first.** Behaviour comes from the games' scripts
  and data and what the executables do, made to work for every module at
  once. No per-module patches, no rewriting a game's script logic natively.
  Survey every rule the reference applies to an area before building it.

## Licensing

kjk is MIT ([`LICENSE`](LICENSE)), and so is every contribution: by
opening a pull request you agree to license your change under it.

- **Never copy or translate code from a GPL project** (OpenJK, Quake III,
  reone, xoreos), not even a line, a table or a constant's name. Read them
  for behaviour only, write down what the behaviour is in your own words,
  and write our code from that description.
- Their identifiers stay out of our code and docs (`PM_…`, `WP_…`,
  `saberMoveData`, `pmove_t`, …), and so do phrases such as "port of" or
  "adapted from" next to their names. `cargo xtask publish-check` refuses
  these shapes; the few places that may name a reference project are on
  its allow-list.
- A new dependency must carry a licence on the accepted list in
  [`deny.toml`](deny.toml) (`cargo deny check licenses`). Binary releases
  ship `THIRD-PARTY-LICENSES.html`, generated by `cargo about` from
  [`about.toml`](about.toml).

## Branches and pull requests

The following branch policy applies to the fork `shadowndacorner/kjk`.
The upstream repository is `kjk-engine/kjk`. Its own contribution
instructions still apply to pull requests opened there.

### Long-lived branches in the fork

| Branch | Purpose | Allowed changes |
| --- | --- | --- |
| `main` | Exact mirror of upstream `main` | Verified fast-forwards from upstream only. Never merge a fork PR here. |
| `develop` | Integration of generally useful improvements | Reviewed, upstream-compatible fixes, features and tests. Fork workflow instructions and the minimal CI and release plumbing needed to build develop are scoped administrative exceptions and must stay out of upstream PRs. |
| `custom` | The fork's customized playable distribution | Reviewed fork-specific features, tuning, delivery tooling, and everything integrated into develop. |

The normal flow of changes is `upstream/main` → `main` → `develop` →
`custom`. The maintainer or authorized coordinator performs these syncs.
Check the exact tips and ancestry before moving a ref. If upstream
rewrites its history or a fast-forward is not possible, stop and request
a decision. Do not force-push a long-lived branch. Merge the upstream
mirror into develop, and develop into custom, when necessary to preserve
already published history. Never merge custom wholesale into develop
or develop wholesale into main. Use reviewed integration PRs when a
non-fast-forward merge is required.

### Feature branches

- For a self-contained upstream candidate, start `fix/<topic>` or
  `feat/<topic>` from the current fork main. Open the internal PR
  against develop. Keep the feature head free of unrelated develop
  commits, fork workflow instructions, custom changes and release policy.
  Submit the isolated branch to upstream main once qualified and approved.
- If a generally useful feature depends on unmerged develop work, start
  from develop and target develop. Record the dependency. Before
  submitting upstream, create a new clean branch from current main and
  port only the intended changes, or wait for prerequisites to land upstream.
  Requalify the exact upstream candidate.
- Start fork-only work from custom, name the branch `fork/<topic>`, and
  target custom. Examples are optional gameplay changes, balance defaults,
  and the device updater. Git cannot have both a branch called custom and
  branches called custom/<topic>.
- If a custom feature becomes useful upstream, extract its reusable part
  onto a new clean main-based branch. Do not merge the custom branch back.
- Use separate worktrees and record the base commit, target, dependency
  order and evidence for each PR. Do not rewrite a shared or published
  branch. Create a replacement branch when necessary; retain the original
  until its work and evidence have been reconciled.
- After an upstream squash merge, sync main into develop and custom in
  order. Check the patch equivalence and resulting tree, resolving only
  residual differences. Never reapply an already accepted change merely
  because its commit SHA differs.
- All features need the existing review and qualification gates. This
  policy does not authorize agents to merge, publish or bypass gates.

### Builds and releases

The delivery implementation is tracked in fork issue #66 and PR #71.
These are target contracts, not claims that the CI or updater has been
implemented or qualified on this baseline.

| Source | Channel and tag policy |
| --- | --- |
| `main` | Verify the upstream baseline. The upstream channel uses upstream's own published releases; do not create fork stable tags on main. |
| `develop` | General integration prereleases, `kjk-dev-*`. |
| `custom` | Customized development prereleases, `kjk-custom-dev-*`. |
| `release/<version>` cut from custom, or a qualified custom commit | Customized stable releases, `kjk-custom-vMAJOR.MINOR.PATCH`. |

A release branch is optional and never merges into main or develop.
Propagate generally useful fixes through a clean develop-targeted PR;
reconcile custom-only release fixes into custom. Record the exact source
branch, commit, channel and tag in every fork release manifest. A tag
must resolve to the qualified source commit and have the correct source
ancestry and explicit channel provenance. The tag name alone is not
enough. Dev builds must never be Latest; stable promotion remains an
owner decision. The updater should expose upstream, develop, custom
development and custom stable channels, with custom stable the default
for our distribution. Retain the existing native Rust requirement and
all publication and actual-device qualification gates. All feature PRs
must receive automated build and regression checks.

### Upstream repository contributions

- Never commit to `main`. Work on a branch named `<you>/<topic>`, ideally
  in its own git worktree (`docs/BUILD.md` on seeding its `target/`).
- Open a pull request against `main`. CI runs two jobs: **tests**
  (publish check, licences, fmt, the approved tests) and **clippy** (both lints).
- The maintainer reviews and squash-merges: the pull request's title and
  description become its one commit on `main`, so write them as that
  commit's message.
- Pushed history is never rewritten. To catch up with `main`, merge it into
  your branch.
- Commit messages say the effect in plain words ("Silent shouts carry only
  as far as a creature hears"), not the files touched.

## The gate, before every commit

From the repository (or worktree) root:

```bash
cargo fmt --all -- --check \
  && cargo clippy -q --workspace --all-targets --all-features -- -D warnings \
  && cargo test --release -p approved_tests -p launcher --test approved
```

Naming `launcher` builds the tests with the same dependency features as
`kjk`, so they reuse its build instead of compiling the sim a second time.
CI runs the plain `cargo test --release -p approved_tests`.

A change to what the verbs share with play also gets
`cargo clippy -q -p launcher --all-targets --no-default-features -- -D warnings`.
`cargo test --release -p approved_tests --features rig` adds the skeleton
jolt ceilings, which need the game installs. Write files with LF endings.

## Tests, probes and the sim hash

- **Permanent tests live only in `crates/approved_tests`**, and only for
  scenarios the maintainer approved by name ([`docs/TESTS.md`](docs/TESTS.md)).
  Checks you want while working are probes (`kjk sim probes`, `kjk combat …`,
  `kjk script …`), not new `#[test]`s.
- **The sim is deterministic** and its final hash after a fixed run is
  pinned in `bumps/SIM_HASH`.
  It moves only on purpose, and only the pin before a release writes it: say why in
  `bumps/<branch>.toml` (`sim = "…"`) and in the pull request
  ([`bumps/README.md`](bumps/README.md)).
- **Snapshot, save and recording formats** carry version tags (KJKS, KJKV,
  KJKR, …). When you change one, don't edit its number: add its history
  line under `[formats]` in the same bump file, and the pin before a release numbers it.

## Walkthroughs

The campaign is played headless as a chain of routes
([`docs/PLAYTESTS.md`](docs/PLAYTESTS.md)). While working, replay the route
your change touches from its checkpoint (`kjk chain k1 ROUTE --alone`).
Before a merge, run `kjk chain k1` from the first route your change can
reach; after any change to the sim or the playthrough harness, the whole
chain to both endings (an unchanged sim hash proves nothing about the
chain). A run stops at its first block. Never rerun a blocked route on an
unchanged build: the sim is deterministic, so it blocks the same way (the
chain's cache answers such a rerun without playing it). A route that blocks
is fixed by the rule that let it happen, with a probe, never by editing the
route around it.

## Quirks

A reference bug we reproduce gets an entry in `QUIRKS.md`. Ask the
maintainer for a range of numbers before adding one; never take the next
free number, since parallel branches collide on it.

## Working with an agent

`AGENT.md` is written for agents and applies to yours. A new worktree's
`target/` can start as a clone of the main checkout's (`docs/BUILD.md`). Long builds and playthroughs
run in the background; never poll them in a loop. Agents never push to or
merge into `main`.

## Bug reports

Check [`KNOWN-ISSUES.md`](KNOWN-ISSUES.md) first; what is listed there is
known. A useful report contains:

* the commit;
* OS and GPU;
* which game's data (KOTOR 1, KOTOR 2 or Jedi Academy; Steam, GOG or disc)
  and which module;
* the steps, and what happened instead; the run folder under
  `kjk-artifacts/runs/` if there is one (a release build keeps its runs in
  `logs/` in the settings folder, `docs/RELEASE.md`).

Do not attach your `.env`, a memory dump, or any game file.
